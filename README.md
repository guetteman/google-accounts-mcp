# google-accounts-mcp

An MCP server that lets your AI agents use several Google accounts at once: personal gmail.com accounts and Google Workspace accounts from any organization. You decide what each agent connection can do in each account, and every tool call is recorded.

You deploy it to your own Cloudflare account, with your own Google Cloud OAuth client. Gmail comes first; other Google services follow.

**Status:** owner sign-in through Cloudflare Access and MCP connections for Claude, Claude Code, and ChatGPT are implemented. The owner can manage Google accounts and set each connection's tools to Not allowed, Ask first, or Allowed, individually or for a whole account. Tools are grouped by job. Changing a whole account to Ask first or Allowed asks for confirmation. For Allowed, the confirmation names each tool whose effect cannot be undone, and setting one such tool to Allowed asks for confirmation too. Connections start with no access. Each connection lists only account tools set to Ask first or Allowed on at least one account. The server announces a changed tool list to clients that listen. `list_accounts` returns accounts with at least one tool set to Ask first or Allowed. Calling a denied tool on one of those accounts returns `tool_not_allowed` with a link to the connection's settings. An account with every tool denied stays hidden. `list_labels` lists an account's Gmail labels, and `search_threads` searches the mail of one account with a Gmail query; an agent calls it once for each account. `read_thread` reads a thread as plain text, with attachment names and pages for long threads. Reading leaves unread mail unread. `change_labels` archives threads, marks them read or unread, and adds or removes labels; it refuses the trash and spam labels. One call names at most 15 threads so that approving it stays within the 50 subrequests of the Workers Free plan. `create_draft` writes a new draft or a reply with a plain text body; nothing is sent. `send_message` sends a new message, `send_reply` replies in its thread, `forward_message` forwards the original text and every attachment, and `send_draft` sends an existing draft as it is in Gmail. Sent mail cannot be taken back. A forward carries at most 20 attachments and 25,000,000 bytes of attachments and text. The original's text must fit 2,000,000 bytes of body, 1,000,000 characters, and three body parts that Gmail gives apart; otherwise it is not forwarded. Parts that are neither plain/HTML text nor attachments, such as a calendar invitation without a file name or attachment ID, are omitted. Repeating the same arguments from one connection within seven days returns the first result, a running or unknown status, or its pending approval. The three composing send tools and `create_draft` accept `duplicate: 2` for another copy on purpose. `send_draft` accepts no `duplicate`. An unknown outcome asks the owner to look in Gmail before requesting another copy. `trash_messages` moves named messages to the trash, `restore_messages` takes them out, and `delete_messages` deletes them permanently. Each accepts up to 15 message IDs from one account. Permanent deletion cannot be undone. Their results list the messages that changed, with label IDs for trash and restore. `not_found` lists IDs that the account does not have, and `unconfirmed` lists IDs for which Google did not confirm the change; retry those IDs. Empty lists are omitted. A call returns an error when Google confirms the change for none of the messages. `get_attachment` downloads one attachment, up to 12 MB, as an embedded resource in Claude Code or as an image or text in other clients. With Ask first, an account tool returns an approval link without contacting Google. The signed-in owner approves or rejects on that page; approving runs the call once, and the agent collects its outcome with `get_approval`. Approvals expire after one hour. Tokens and the arguments and results retained for approvals are encrypted in D1. Retained files are encrypted in KV. Downloads keep their references inside sealed results; uploads keep theirs in sealed upload rows or approval arguments. Same-call records hold only a keyed identity, a claim, times, and Gmail IDs. Every tool call is recorded; a missing outcome means the result is unknown. A search makes one request to Gmail for the list and one for each thread, at most 26, which fits the subrequest limit that Cloudflare documents for the Workers Free plan. A page for viewing these records and more Gmail tools are planned in the [issues](../../issues).

Before deploying this version, apply all pending migrations through `migrations/0007_uploads.sql` to the deploy's D1 database with `pnpm exec wrangler d1 migrations apply DB --remote`. This includes migrations 0004, 0005, and 0006 if they have not been applied. Use the same configuration and environment as the Worker. Deploy the code only after the migrations succeed. Migration 0005 preserves existing allowed permissions; migration 0006 preserves existing approvals and adds the records that prevent repeated drafts and repeated sends. Migration 0007 adds upload links and the other accounts used by a call to its audit record. Without migration 0005, connection pages fail closed; revoking a connection, removing an account, and setting a tool to deny return HTTP 503 and change nothing. Account tool calls fail without an audit record. Deploying this version creates a cron trigger (`*/10 * * * *`) that cleans up approvals, expired uploads, and expired same-call records every ten minutes. It also creates a second KV namespace for files, with no extra setup step. Downloaded files expire after about one hour.

An agent that controls a browser where the owner is signed in can approve its own call or change its own settings. The server cannot distinguish those browser actions from the owner's actions.

Browser tests use Chromium. After `vp install`, run `pnpm exec playwright-core install chromium` once before `vp test run`. CI installs Chromium and its system dependencies.

`create_draft`, `send_message`, and `send_reply` accept up to 6 attachments, with at most 25,000,000 bytes of files and UTF-8 body text together. A copy is `{ account, message, attachment }`, using the IDs listed by `read_thread`. It needs both the composing tool's setting on the sending account and `get_attachment` on the source account. One Ask first setting makes the whole call wait for one approval, whose page names every account. Copies go straight into the mail and do not pass through a tool result. `forward_message` and `send_draft` do not accept this field.

Configure two Cloudflare Access self-hosted applications for the Worker hostname. The application for the whole hostname needs an Allow policy restricted to the owner's email address. Its Application Audience (AUD) Tag supplies `ACCESS_AUDIENCE`. A second application covers the more specific paths `/mcp`, `/oauth/*`, `/.well-known/*`, and `/uploads/*`, with a Bypass policy for everyone. These paths use the server's own connection or upload credentials instead of an Access session. Keep owner pages under the first application. Without the Bypass path for `/uploads/*`, a file upload gets an Access sign-in page.

For local files, `create_upload_link` takes no input and returns `{ url, expires_at }`. Send one file with `PUT <url><percent-encoded filename>`, its raw bytes as the body, and its media type in `Content-Type`. For example, `curl -sS -T report.pdf -H 'Content-Type: application/pdf' '<url>'` appends the file name because the URL ends in a slash. Do not send a form. The JSON answer gives `{ upload, filename, type, size, expires_at }`. Check the metadata and name that ID as `{ upload }` in `attachments`. Only the connection that asked for the link can attach its file. The link takes one file of at most 25,000,000 bytes, once. A file name is part of the address and appears in the Worker's request log even after the file expires.

A link and its unused file expire 15 minutes after the link was created. A successful or unknown call consumes its uploads; a failure that created nothing leaves them available for a retry. Taking a file into an approval consumes the upload and keeps its encrypted reference in that approval for up to one more hour. Rejecting, expiring, ending, or deciding the approval erases those stored arguments. The file's encrypted bytes expire in KV one hour and one minute after the link's expiry. A repeat with exactly the same arguments returns the existing result or approval; another message needs a new upload. A lost PUT answer also needs a new link, because only that answer gives the upload ID.
