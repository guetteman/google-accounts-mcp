# google-accounts-mcp

This server lets one person's AI agents use several Google accounts at once: personal gmail.com accounts and Google Workspace accounts from any organization. The official connectors allow one account per client, and that is the gap we fill. Gmail comes first; other Google services follow, so do not design anything that only works for Gmail when it is as easy to keep it general.

Each deploy has one owner, who runs it on their own Cloudflare account with their own Google Cloud OAuth client. The repository is public so that anyone can deploy it, and a new owner must be able to deploy without editing code.

The server holds access to private mailboxes, so the owner's control comes before agent convenience. Each connection gets only the accounts and actions the owner granted, and every agent action is recorded in an audit log the owner can read. When two designs are both valid, choose the one that grants less by default and fails closed.

Reviewers apply `CODING_STANDARDS.md`; read it before you change code.

When you design or prototype a page, start from shadcn components and apply Refactoring UI (Wathan and Schoger) without inventing UI outside shadcn: build hierarchy with size, weight, and color before borders; de-emphasize labels and secondary text so the data stands out; avoid boxes inside boxes and keep a border only on what needs attention; give each screen one primary action; use generous, consistent spacing. Render it at 390 px and at desktop width and look at it before you show it.

- Write everything in this repository in English: code, docs, issues, pull requests, and product text. Issues live in this repository's GitHub tracker.
- The owner's Google accounts hold real mail. Call Google APIs against them only with the owner's permission, and never send, delete, or change mail in a real account without the owner's explicit approval for that action.
- Agents must never deploy.
- Keep `.gitignore` in place before you run `vp check --fix`; otherwise it can rewrite `node_modules` and corrupt the pnpm store.
- When you stop `pnpm dev`, stop its entire process group so that Vite and workerd do not keep running.

## Local development and verification

- Install dependencies with `vp install`. Run `vp check`, `pnpm exec wrangler types --check`, `vp test run`, and `vp build` before handing off a change. Tests include Worker tests in workerd, Node tests for the reset command, and Chromium tests for the Connections and Accounts dialogs, the approval page, and the individual-tool and whole-account permission controls, including confirmation, grouped tools, and lost responses, with fake Access signing keys, a fake certs endpoint, and `msw` serving the three clients' metadata documents. Run `pnpm exec playwright-core install chromium` once before the first `vp test run`.
- Run `vp dev` for page previews at `/__pages/:id`: `access-refused`, `access-unavailable`, `not-owner`, `mismatch`, `setup-incomplete`, `setup-incomplete-two`, `unavailable`, `accounts`, `accounts-empty`, `connections`, `connections-empty`, `connection-new-connection`, `connection-some-allowed`, `connection-all-allowed`, `connection-no-accounts`, `connection-ended-connection`, `connection-save-failed`, `consent-claude-code`, `consent-claude`, `consent-chatgpt`, `client-refused`, `consent-expired`, `approval-waiting`, `approval-waiting-long-names`, `approval-waiting-search`, `approval-waiting-notes`, `approval-waiting-labels`, `approval-waiting-labels-many`, `approval-waiting-thread`, `approval-waiting-attachment`, `approval-waiting-draft`, `approval-waiting-reply`, `approval-cannot-show`, `approval-changed`, `approval-running`, `approval-succeeded`, `approval-failed`, `approval-unknown`, `approval-rejected`, `approval-expired`, `approval-ended-tool`, `approval-ended-connection`, `approval-ended-account`, and `approval-unconfirmed`. Previews pass through the owner gate, so they need a `.dev.vars` with the six settings (`OWNER_EMAIL=alex.personal@example.com`, `ACCESS_ISSUER=https://example-team.cloudflareaccess.com`, a 64-hex `ACCESS_AUDIENCE`, `GOOGLE_CLIENT_ID=test-client.apps.googleusercontent.com`, `GOOGLE_CLIENT_SECRET=fake`, and a 64-hex `TOKEN_KEY` are enough) and the migration applied with `pnpm exec wrangler d1 migrations apply DB --local`. The connection previews show Not allowed on every tool in `connection-new-connection`, Ask first on all Personal tools and mixed settings on Projects in `connection-some-allowed` and `connection-save-failed`, and Allowed on all tools of all four accounts in `connection-all-allowed`. The `connection-save-failed` preview also starts with the persistent database failure notice. These previews exist only in development builds. A real local Google flow requires `http://localhost:<port>/google/callback` registered on its OAuth client. Local OAuth flows work over plain HTTP only on loopback hosts such as `localhost`; reviewing OAuth over Tailscale needs HTTPS, for example `tailscale serve`. Page previews still work over plain HTTP on Tailscale.
- Use `pnpm owner:reset --local` to reset local D1. The command defaults to remote D1 when `--local` is omitted. It reports the database, configuration, environment, stored owner, and generation before asking for confirmation. It takes the environment from `--env` or the `CLOUDFLARE_ENV` environment variable, not from `.env` files, and guards every statement on the database's `instance`, so a reset confirmed for one database changes nothing in another. Pass `--persist-to`, `--env`, or `--config` to select the same database as the local Worker.
- Until `wrangler.jsonc` has a `database_id`, local D1 state is keyed by the `DB` binding. Adding an ID switches to a different local database; apply migrations to that database before using it.

## Gmail tools

- `list_labels` lists labels, `search_threads` finds mail, and `read_thread` reads full threads.
- `create_draft` writes a new draft or a reply, with a plain text body. It sends nothing. Identical calls from one connection are answered as repeats for seven days; `duplicate` requests another copy.
